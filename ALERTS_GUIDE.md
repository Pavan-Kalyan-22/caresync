# CareSync Alerts & Reminders Engine Guide 🔔

This guide details the architecture, REST endpoints, alert condition rules, graceful degradation strategies, and security configuration for **Task 7 — Alerts / Reminders** in the CareSync Healthcare backend.

---

> [!IMPORTANT]
> **Product Wellness Notice**:  
> The alerts and reminders generated by CareSync are dynamic software product heuristics intended for everyday hydration motivation and general wellness awareness. They are **NOT** clinical medical diagnoses, medical warnings, healthcare prescriptions, or medical advice.

---

## 1. Architecture & Design Principles

The Alerts / Reminders module provides a dynamic, read-only, on-the-fly evaluation engine:

```text
HTTP Client (Web / Mobile)
   │
   └── GET /api/v1/alerts?city=... OR ?lat=...&lon=...
         │ (Requires JWT Bearer token)
         ▼
       AlertsController
         │ Extracts caller email via authentication.getName() (NO userId parameter)
         ▼
       AlertsServiceImpl
         │ 1. Validates user profile from UserRepository
         │ 2. Calculates today's intake from WaterIntakeRepository [startOfDay, endOfDay)
         │ 3. Resolves daily target & ambient temperature:
         │      ├── If location provided: calls HydrationService (live weather target)
         │      └── If location omitted or weather fails: falls back to baseline target
         ▼
       AlertRuleEngine (Single Source of Truth)
         │ Evaluates active condition predicates:
         │  ├── isHighTemperature (>= 35°C) -> HIGH_TEMPERATURE (WARNING)
         │  ├── isHydrationGoalReached (consumed >= target) -> HYDRATION_GOAL_REACHED (INFO)
         │  └── isHydrationReminder (consumed == 0) -> HYDRATION_REMINDER (INFO)
         ▼
       ApiResponse<AlertsResponse> (HTTP 200 OK)
```

### Core Architecture Guardrails
1. **Dynamic & Read-Only**: Alerts are evaluated dynamically per request. There is **no Alert database table**, no `Alert` entity, no persistence, and no alert state (e.g. read/unread).
2. **Zero Notification Infrastructure**: No WebSockets, FCM, Firebase, push notifications, emails, SMS, Kafka, RabbitMQ, schedulers, or background workers.
3. **Single Source of Truth**: `AlertRuleEngine` centralizes all alert threshold constants (`35.0°C`, `30.0°C`, `28.0°C/70%`) and condition logic, shared by both Task 6 Dashboard and Task 7 Alerts without rule duplication.

## 2. API Specification

### Endpoint
```http
GET /api/v1/alerts
```

### Security
- **Authentication**: Required via `Authorization: Bearer <JWT_TOKEN>`.
- **Identity Isolation**: The caller's identity is derived strictly from `authentication.getName()`. The API does not accept `userId`, `email`, or username request parameters.

### Query Parameters

| Parameter | Type | Required | Description | Example |
|---|---|---|---|---|
| `city` | String | Optional | City name for live ambient weather evaluation | `Bengaluru` |
| `lat` | Double | Optional | Latitude coordinate (-90 to +90) | `12.9716` |
| `lon` | Double | Optional | Longitude coordinate (-180 to +180) | `77.5946` |

*Note: When both `city` and coordinates are passed, coordinates take precedence. If partial coordinates are provided (e.g., `lat` without `lon`), the API returns `400 Bad Request`.*

## 3. Supported Alert Types & Rules

Task 7 initially supports the following 3 hydration-related alerts:

| Alert Type | Severity | Title | Message | Trigger Condition |
|---|---|---|---|---|
| `HIGH_TEMPERATURE` | `WARNING` | `High temperature` | `Stay hydrated today.` | Current ambient temperature $\ge 35^\circ\text{C}$ |
| `HYDRATION_GOAL_REACHED` | `INFO` | `Daily goal achieved` | `You have reached your daily hydration goal.` | Today's water consumed $\ge$ today's hydration target |
| `HYDRATION_REMINDER` | `INFO` | `Hydration reminder` | `You have not logged any water intake today.` | Today's water consumed $== 0\text{ ml}$ |

### Alert Combination Behavior
Multiple alerts can be returned concurrently:
- If temperature is $36^\circ\text{C}$ and consumed water is $0\text{ ml}$, the response contains both `HIGH_TEMPERATURE` and `HYDRATION_REMINDER`.
- If temperature is $36^\circ\text{C}$ and daily target is achieved, the response contains both `HIGH_TEMPERATURE` and `HYDRATION_GOAL_REACHED`.
- If temperature is below $35^\circ\text{C}$ and consumed water is between $0\text{ ml}$ and target, zero alerts are returned (`alerts: []`, `count: 0`).

---

## 4. Weather Failure & Fallback Behavior

- When external weather services (OpenWeatherMap) are unreachable or fail, the alerts endpoint **does not fail**.
- The API gracefully falls back:
  1. `temperature` is set to `null` $\rightarrow$ `HIGH_TEMPERATURE` is omitted (no fabricated weather).
  2. Daily target falls back to the user profile baseline target:
     $$\text{Baseline Target (ml)} = \text{Clamp}(\text{Weight(kg)} \times 35\text{ ml/kg} + \text{Activity Adjustment}, 1500, 4500)$$
  3. Hydration intake alerts (`HYDRATION_REMINDER` and `HYDRATION_GOAL_REACHED`) continue to be evaluated against the baseline target.
  4. The endpoint returns `HTTP 200 OK` with available hydration alerts.

## 6. Error Responses

| Status Code | Reason | Example Scenario |
|---|---|---|
| `400 BAD REQUEST` | Validation error | Incomplete coordinates (`lat` without `lon`) |
| `401 UNAUTHORIZED` | Authentication error | Missing, invalid, or expired JWT token |
| `404 NOT FOUND` | Resource error | Authenticated user not found in database |
